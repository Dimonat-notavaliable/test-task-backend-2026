# Результат выполнения тестового задания
Точка входа — `collect_leads_customers(is_full=True)`.
Нагрузка: 20 тыс. покупателей и 50 тыс. сделок.

Для возможности запуска необходимо сформировать и осуществить миграцию на основании имеющейся схемы БД.
## Неоптимальные части исходного кода
- На каждую отдельную сущность выполнялись запросы (порядка 250 тыс. на описанную нагрузку) и коммиты (70 тыс. на описанную нагрузку).
- Поиск осуществлялся с использованием оператора @> без индекса.
- При финальной очисте полностью читалась вся таблица.
## Изменения
- Изменена схема хранения данных (поля из general определены как отдельные столбцы). Определены отдельные таблицы: `abstract_customer`, `amo_customer`, `amo_lead`, `abstract_contact`, `abstract_company`. Для сделок и покупателей добавлены индексы по `login`, `name`, `abstract_id`.
- Переработан алгоритм синхронизации (определен в файле `sync.py` в классе `CrmSync`):
1. В память загружаются только идентифицирубщие поля (`amo_id`, `abstract_id`, `login`);
2. Покупатели и сделки читаются потоком, сформированы словари для поиска по id и логину;
3. Запись осуществляется пакетами по 1000 строк (размер настраиваемый), неизмененные строки не переписываются;
4. Слияние записей осуществляется в конце одним набором запросов;
5. Устаревшие сущности удаляются только после полного прохода по полученной информации;
6. Любая ошибка полностью откатывает транзакцию.

Расчетный результат: порядка сотни запросов и 50-150 МБ памяти процесса.

- Константы статусов 111349 и 143 для пропуска. Так как нет информации об их значении в CRM.
